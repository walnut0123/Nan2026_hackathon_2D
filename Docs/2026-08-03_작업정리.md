## 2. 방 판정 로직 Q&A

### 2-1. 게임 시작 시 "시작 방" 판정 방식

`RoomController.lockOnStart` 플래그로 처리됨을 확인·설명. 다른 방은 `RoomBoundsTrigger`가
플레이어 발밑 콜라이더(`PlayerInventory`)를 감지해 `NotifyPlayerEntered()`를 호출하지만,
시작 방은 플레이어가 트리거 밖에서 들어오는 게 아니라 처음부터 안에 있으므로 `Start()`에서
직접 호출. 당시 `lockOnStart=true`인 오브젝트는 `RoomA_Entrance`(입구방) 하나뿐이었음.

### 2-2. RoomA/RoomC의 `Bounds_X` vs RoomB만 있는 `EntranceTrigger_East/South`

RoomB_Boss만 트리거가 2개(`EntranceTrigger_East`, `EntranceTrigger_South`)인 이유를 씬
파일 grep으로 추적: RoomB_Boss(보스방, grid (0,0))는 RoomA_Entrance(입구방, (0,-1))와
RoomC_Combat(전투방, (1,0)) **두 방과 동시에 인접**해서 진입로가 2곳 필요했던 것. 입구방·
전투방은 인접한 방이 하나뿐이라 `Bounds_A`/`Bounds_B` 하나면 충분했음.

## 3. Room 구조 전면 재편 — `Rooms > Map1~Map4`

### 배경

기존 Demo 방(RoomA_Entrance/RoomB_Boss/RoomC_Combat)을 실제 맵 아트(`Map_1` 토끼굴,
`Map_2` 티파티, 이미 배치되어 있었음)에 맞춰 `Map1~Map4` 체인 구조로 정리해달라는 요청.
사용자에게 확인받은 주요 결정 사항:

| 질문 | 답변 |
|---|---|
| RoomB_Boss/RoomC_Combat 중 Map3/Map4는? | RoomB→Map3, RoomC→Map4. "전투방" 개념 폐지(모든 맵에서 전투), 접미사(Boss/Combat) 제거하고 단순하게 |
| 기존 배치된 Map_1/Map_2 아트를 Room 로직 밑으로 재부모화할지? | 아니오 — 각 Map 오브젝트 하위에 기존 아트(건드리지 않음) + 신규 `Logic` 자식만 추가. 마지막에 `Rooms` 오브젝트 하나 새로 만들어 Map1~4를 그 밑에 배치 |
| RoomB_Boss의 깨진 `Door_South` 참조 처리 | 목록에서 제거(당장 만들 수 없는 참조만 제거, 실제 오브젝트는 안 건드림) |

### 실행 내용

- `RoomA_Entrance` → `Map_1/Logic`으로 이동, 자식 `Door_South` → `Map2_exit`로 개명
  (※ 이 명명은 이후 4절에서 다시 수정됨), `roomName`을 `"Map1"`로 단순화
- `Map_3` 신규 생성 → `Heart_Queen_Palace`(신규 그룹, 씬 루트에 흩어져 있던
  `Box_A_Closed`/`Tree_A`/`Tree_B`/`Vase_TypeA×2` 이동) + `Logic`(← `RoomB_Boss` 이동,
  `EntranceTrigger_South`→`Map3_entrance`, `EntranceTrigger_East`→`Map3_exit`,
  `Door_A`→`Map3_exit`)
- Map3_entrance용 **신규 문 오브젝트** 제작(기존엔 감지 트리거만 있고 실제로 잠기는 문이
  없었음) — `BoxCollider2D`+`DoorController` 추가, `blockingCollider` 연결, `doors[]`에
  등록(컴포넌트 instanceID로 참조해야 정상 연결됨 — GameObject instanceID로 시도하면
  `doors:[null]`로 깨지는 것 확인 후 수정)
- `Map_4` 신규 생성 → `Logic`(← `RoomC_Combat` 이동, `Door_B`→`Map4_entrance`,
  `Bounds_B`→`Map4_entrance`), `roomName` → `"Map4"`
- 기존 `Rooms` 오브젝트(빈 상태가 됨)를 재사용해 `Map_1`/`Map_2`/`Map_3`/`Map_4`를 그 밑에
  재부모화 — 전 과정 월드 좌표 유지(world-space-preserving reparent) 방식으로 진행해
  화면상 위치는 변경 없음

## 4. Map1/Map2 좌표 버그 발견 및 수정

### 증상

"플레이어 현재 위치가 사실 Map2임", "Map1/Logic/Map2_exit이 사실 Map2 클리어 후 열리는
문처럼 보인다"는 리포트.

### 원인 (Scene View 스크린샷으로 확인)

`Map_1`/`Map_2` 최상위 컨테이너의 Transform.position 자체가 실제 아트 위치와 무관한
역사적 오프셋을 갖고 있었음 — 진짜 아트(`The_Rabbit_Hole`, `The_Mad_Tea_Party`)는 각각
컨테이너 하위에서 **보정 오프셋**을 갖고 있어, 실제 월드 위치는:

- 토끼굴(Map1 아트): 월드 `(-9.6, -22.9)` — 완전히 고립된 먼 곳
- 티파티(Map2 아트): 월드 `(0.2, -7.4)` — 옛 Demo 방들(월드 원점 근처)과 거의 같은 자리

3절에서 "월드 좌표 유지"로 `RoomA_Entrance`를 `Map_1` 밑으로 옮겼을 때, RoomA_Entrance는
원래 월드 원점에 있었기 때문에 실제로는 티파티(Map2) 바로 옆에 남아있게 된 것 — 결과적으로
"Map1의 로직"이 Map2 근처에, 진짜 토끼굴 자리에는 로직이 하나도 없는 상태가 됨.

### 수정

- 기존 `Map_1/Logic`(문+Bounds)을 **`Map_2/Logic`으로 이동**, 문 이름을 원래 의도대로
  `Map2_exit`로 되돌림, `lockOnStart` 끄고 `RoomMonsterSpawner` 컴포넌트 신규 추가
- 토끼굴 실제 위치(-9.6,-22.9)에 **새 `Map_1/Logic` 생성**: `lockOnStart=true`, 몬스터
  없음(즉시 클리어), 통로(`Corridor_1TO2`) 방향에 실제 `Map1_exit` 문 신설(벽 콜라이더
  9개 좌표로 방 경계 역산해 배치)
- `Map2` 쪽에 `Map2_entrance` 트리거 신규 생성(Map1↔Map2 통로 상단, `Map1_exit`와 좌표
  계산으로 매칭해 배치) — Map2의 RoomController에 연결
- 플레이어를 토끼굴(Map1) 내부 `(-10, -20.7)`로 이동 — Scene View 스크린샷으로 실제
  청록색 방 안에 들어간 것 확인
- Map3의 entrance/exit 중복 이름 문제(트리거+문이 각각 별도 오브젝트로 이름이 같았던 것)는
  **한 오브젝트로 병합**하는 방식으로 해결 — `BoxCollider2D`를 하나 더 추가해 문(막는
  콜라이더)과 트리거(감지용)를 같은 오브젝트에 공존시킴. 기존 트리거 전용 오브젝트
  (`EntranceTrigger_East`/`South`)는 삭제, 좌표/크기는 원래 트리거와 동일하게 유지해
  기능 손실 없음. Map4는 문(좁은 게이트)과 트리거(방 전체 감지용, `Bounds_B`)의 역할
  범위가 달라 병합하지 않고 트리거만 `Map4_bounds`로 개명

## 6. Map3 입구 판정 버그 진단/수정

### 증상

Map3 입구에서 플레이어가 완전히 입장하지 않았는데도 입장 판정이 뜨면서, 캐릭터가 실제로는
Map3에 못 들어간 채로 몬스터 스폰 등 게임이 그대로 진행됨.

### 원인

4절에서 Map3_entrance를 "문+트리거 병합" 오브젝트로 만들 때, 두 콜라이더가 거의 같은
위치에 겹쳐 있었음. 플레이어가 문턱에 발만 스쳐도 트리거 발동 → `RoomController.LockRoom()`
호출 → 그 자리의 문 콜라이더가 즉시 다시 활성화(잠김) → 아직 문턱을 채 못 지난 플레이어가
물리적으로 도로 Map2 쪽으로 밀려남. 그사이 몬스터 스폰 등 방 로직은 이미 진행되어버림.

### 수정

- `Map3_entrance`의 감지 트리거를 방 내부 방향(+y)으로 밀어 문 콜라이더 범위와 최소
  0.06 unit 여유를 두도록 재배치 — 플레이어가 문턱을 완전히 지나야만 판정이 뜨도록 변경
- 동일 구조 문제가 있는 `Map3_exit`(역방향 진입 대비)도 예방 차원에서 같은 방식으로 미리
  수정
